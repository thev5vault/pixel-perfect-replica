## Stripe integration task

### Objective

Make the minimal changes needed to integrate Stripe Checkout. First detect which scenario applies (see Scenario detection below), then follow only the instructions for that scenario.

### Scenario detection

Scan the codebase for an existing Stripe Checkout Session API call. Look for patterns such as:
- `stripe.checkout.sessions.create(...)`
- `Stripe::Checkout::Session.create(...)` (Ruby)
- Any equivalent in the user's language or framework that creates a Stripe Checkout Session

**Scenario A — Existing Checkout Session API call found**

1. Locate every place in the codebase where a Checkout Session is created.
2. Update ONLY the parameters of that call to match the `fixed_by_ui` values from the Field Intents section below.
3. **Preserve** any `sample_only` parameters (`mode`, `success_url`, `cancel_url`, `line_items`) that already exist in the user's code with real, non-placeholder values. Do NOT replace them with sample placeholders.
4. Remove any parameters that are absent from the Field Intents (they are no longer configured).
5. Do not touch any other code — no new files, no new routes, no refactoring, no restructuring.
6. Create or update `STRIPE_INTEGRATION_TODO.md` only for `sample_only` parameters that are still using placeholder values or are missing from the call.

**Scenario B — No Checkout Session API call found**

1. Add a minimal new server-side endpoint in the user's existing server framework that calls `stripe.checkout.sessions.create(...)` (or `Stripe::Checkout::Session.create(...)` in Ruby).
2. Use the `fixed_by_ui` parameters from Field Intents and the `sample_only` placeholder values from the sample below.
3. Do not add infrastructure that likely already exists (env loading, webhook handlers, middleware, auth). Add only what is verifiably absent.
4. Adapt to the user's language, framework, and conventions. The sample below is a reference only — do not copy it verbatim.
5. Create `STRIPE_INTEGRATION_TODO.md` listing all `sample_only` placeholders and remaining setup steps.

In both scenarios, server-side changes must be surgical and minimal.

### Precedence rules

When instructions conflict, follow this order:
1. `fixed_by_ui` values are authoritative — configured by the user in the Checkout Studio UI. Use as-is.
2. `sample_only` values are placeholders for Scenario B only. In Scenario A, if the parameter already exists in the user's code with a real value, keep the user's value — do NOT overwrite it with a placeholder. Only use `sample_only` placeholders when the parameter is missing entirely from the user's code.

### Rules

1. Adapt to the user's current stack (frameworks, language, auth, DB). Copy only the patterns necessary.
2. **Scenario A only**: Change only the parameters inside the existing Checkout Session creation call. Do not modify surrounding code.
3. **Scenario B only**: Persist and retrieve Stripe resource identifiers (e.g., `customer_id`, `subscription_id`) in the user's datastore, associated with existing domain models — only if the codebase already has a pattern for this.
4. Do not guess the Stripe API version. Leave the API version argument empty when initializing the Stripe client.
5. All `fixed_by_ui` parameters must be used exactly as specified in the Field Intents above.
6. **Scenario B**: All `sample_only` parameters are placeholders — use them as-is, then list each one in `STRIPE_INTEGRATION_TODO.md` with instructions for the user to replace them. **Scenario A**: Keep the user's existing values for `sample_only` parameters; only document them in `STRIPE_INTEGRATION_TODO.md` if they still contain placeholder-like values (e.g., `price_...`).
7. When the task is complete, direct the user to `STRIPE_INTEGRATION_TODO.md` as the single source of truth for remaining setup steps.
8. The `mode` parameter must match the product type: use `"payment"` for one-time charges or `"subscription"` for recurring billing. Only include `payment_method_collection` when mode is `"subscription"`.
9. **Environment variable naming consistency**: Ensure that the variables names used in the `.env` file match those referenced in the code. If the project uses Vite, browser-accessible variables must be prefixed with `VITE_` (e.g. `VITE_STRIPE_PUBLISHABLE_KEY`); server-only variables (e.g. `STRIPE_SECRET_KEY`) must NOT use that prefix.
10. **ui_mode versioning**: The `ui_mode` value depends on the user's Stripe SDK version. Check the installed SDK version (e.g., in `package.json`, `Gemfile.lock`, `go.mod`, `requirements.txt`). SDK version 21.0.0 and above use: `hosted_page`. Versions below 21.0.0 use: `hosted`. If you cannot determine the version, default to `hosted_page` and note the version dependency in `STRIPE_INTEGRATION_TODO.md`.

app.post("/api/webhook", express.raw({ type: "application/json" }), (req, res) => {
  const endpointSecret = process.env.STRIPE_WEBHOOK_SECRET;
  let event = req.body;

  if (endpointSecret) {
    const signature = req.headers["stripe-signature"];
    try {
      event = stripe.webhooks.constructEvent(req.body, signature, endpointSecret);
    } catch (err) {
      console.log("Webhook signature verification failed.", err.message);
      return res.sendStatus(400);
